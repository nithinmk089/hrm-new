# SQL Server database migrations

SQL migration scripts are stored in this directory and are applied by the
`IDatabaseMigrator` implementation in the Infrastructure project.

## File naming

Use a zero-padded, increasing numeric prefix followed by a short description:

- `001_CreateHrmsSchema.sql`
- `002_CreateCompanyOrganizationMasters.sql`
- `003_CreateEmployeeManagementTables.sql`
- `004_CreateIdentityAndSecurityTables.sql`
- `005_TenantIdentityAndAuthorizationFoundation.sql`

Once a migration has been applied to any shared environment, do not edit or
delete it. Add a new migration to change the schema.

## Execution

From the repository root, run:

```powershell
dotnet run --project .\src\backend\HRMS.API\HRMS.API.csproj -- --migrate
```

The migration command requires the `ConnectionStrings:Hrms` setting. For local
development, configure it with .NET User Secrets rather than committing
credentials:

```powershell
dotnet user-secrets set "ConnectionStrings:Hrms" "<your SQL Server connection string>" --project .\src\backend\HRMS.API\HRMS.API.csproj
```

Normal API startup does not apply migrations. Run the migration command
explicitly before starting the API after a schema change.

## Safety behavior

- Scripts are applied in filename order.
- The runner creates `dbo.__HrmsSchemaMigrations` to record applied scripts.
- SHA-256 checksums detect changes to scripts that have already been applied.
- A SQL Server application lock prevents concurrent migration processes.
- Pending scripts and their history records are committed in one transaction.
- SQLCMD-style `GO` batch separators are supported when `GO` appears alone on
  a line (an optional trailing SQL comment is allowed).
- A migration failure rolls back the pending migration transaction.

## Identity and security model

Migration 004 introduced the initial HRMS-local identity model. Migration 005
establishes the canonical model:

- `security.Users` is the global identity table. A user can access multiple tenants.
- `security.UserTenantMemberships` controls which tenants a user can enter.
- `security.Roles` and `security.RolePermissions` remain tenant-scoped.
- `security.Permissions` is the central permission catalogue. Migration 005
  verifies the inspected baseline of 11 rows and does not modify permission IDs.
- `security.UserRoleAssignments` combines a tenant role with Tenant, Company,
  or Office scope. Company descendant access is opt-in.
- `security.RefreshTokens` remains tenant-bound and references a valid tenant
  membership.
- `audit.AuditLogs` is the canonical audit store.

Migration 005 adds TenantId to companies and all company-owned HRMS records,
adds same-tenant company hierarchy constraints, and preserves legacy `hrms`
identity/security/audit tables as deprecated objects. They are deliberately
not dropped until application code has migrated to the canonical tables.

A user may hold different roles/scopes in different tenants. API code must
resolve the authenticated tenant and enforce permission plus scope together;
client-supplied TenantId, CompanyId, or OfficeId values are never trusted alone.

Passwords must be stored only as adaptive password hashes generated by the
application's password-hashing service. Refresh tokens must be cryptographically
random, returned only to the client, and stored in the database as SHA-256
hashes. Never log passwords, access tokens, or refresh tokens.
